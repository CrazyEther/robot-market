# ADR-0006: события ресурсов и политика диспетчеризации

Дата: 2026-09-27. Статус: частично реализован; предметные ограничения маршрута требуют источников T14–T16.

## Контекст

Журнал заданий даёт наблюдённые времена поступления, календарь — интервалы состояния каждого робота, а топология — измеренные точки и длины маршрута. Эти файлы не описывают вместимость узких проходов, правила приоритета или совместное использование лифта. Телеметрия другого объекта не переносится в календарь проекта.

## Текущий контракт

- Порядок обслуживания — FIFO по времени поступления и строке исходного журнала. Позднее задание не начинает цикл раньше принятого предыдущего. При одинаковом возможном времени старта выбор робота детерминирован по времени завершения и идентификатору слота.
- Цикл назначается только внутрь подтверждённого окна `available`. Никаких поступлений, отказов, зарядок и простоев движок не генерирует. Если первое задание очереди не помещается ни в одно будущее окно, поздние задания не обходят его.
- `SimulationRun` сохраняет версию алгоритма, входной снимок и рассчитанный ledger. При открытии исходные байты журнала и календаря проверяются по SHA-256 и расчёт повторяется; изменение сегодняшнего каталога не меняет старый прогон.
- Для проигрывания к сохранённым событиям заданий добавляются изменения состояний из тех же проверенных строк календаря и граница периода. Это события отображения: они не изменяют KPI или денежный расчёт.

## Следующий контрактный gate

До утверждения пропускной способности конкретной площадки нужно получить из разрешённого источника ограничения каждого конфликтного участка: идентификатор ресурса графа, вместимость, допустимые направления, правило занятия и освобождения, время работы и приоритеты. Схему следует версионировать в ревизии проекта, проверить её на трёх предметных типах и затем расширить событийное ядро так, чтобы очередь, задержки на участках, 2D и финансы происходили из одного прогона. Значения не выводятся из визуальной ширины схемы и не подставляются по умолчанию.

## Последствия

Текущий численный ledger описывает очередь роботов и рабочие окна; он не является подтверждением пропускной способности конфликтных участков. Владелец площадки должен подтвердить, что FIFO соответствует его регламенту. Если регламент иной, новая политика требует отдельной версии событийного контракта и проверки исторических прогонов.
