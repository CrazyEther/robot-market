# ADR-0006: события ресурсов и политика диспетчеризации

Дата: 2026-09-27; обновление 2026-09-28. Статус: ядро занятости v3 подключено к сохранённому прогону для подтверждённых участков; полнота объектной приёмки T14–T16 остаётся открытой.

## Контекст

Журнал заданий даёт наблюдённые времена поступления, календарь — интервалы состояния каждого робота, а топология — измеренные точки и длины маршрута. Эти файлы не описывают вместимость узких проходов, правила приоритета или совместное использование лифта. Телеметрия другого объекта не переносится в календарь проекта.

## Текущий контракт

- Порядок обслуживания — FIFO по времени поступления и строке исходного журнала. Позднее задание не начинает цикл раньше принятого предыдущего. При одинаковом возможном времени старта выбор робота детерминирован по времени завершения и идентификатору слота.
- Цикл назначается только внутрь подтверждённого окна `available`. Никаких поступлений, отказов, зарядок и простоев движок не генерирует. Если первое задание очереди не помещается ни в одно будущее окно, поздние задания не обходят его.
- `SimulationRun` сохраняет версию алгоритма, входной снимок, рассчитанный ledger и для новых прогонов события каждого подтверждённого интервала состояния робота с номером исходной строки. При открытии исходные байты журнала и календаря проверяются по SHA-256, ledger и события ресурсов пересчитываются и сверяются; изменение сегодняшнего каталога не меняет старый прогон. Прогоны, созданные до версии шкалы ресурсов, читаются по прежнему контракту.
- Для проигрывания к сохранённым событиям заданий добавляются события состояний роботов и граница периода. Это события отображения: они не изменяют KPI или денежный расчёт. Непрерывные интервалы берутся только из загруженного полного календаря площадки; отдельные снимки телеметрии не достраиваются до интервалов автоматически.

## Следующий контрактный gate

Для подтверждённого участка требуется идентификатор, вместимость, допустимые направления, режим занятия `entry_to_exit`, рабочие окна ISO-8601 с часовым поясом, подтверждённый источник и приоритет `fifo`. При наличии такого участка ядро v3 резервирует время движения каждого робота; промежуточные ожидания смещают передачу груза и завершение цикла. План и индивидуальные фазы сохраняются, повторно проверяются при открытии и используются одними данными в KPI, 2D/3D и финансовом экспорте. При отсутствии подтверждённых общих участков сохраняется исходный алгоритм v2, который не моделирует узкие места.

Следующий gate — независимая предметная приёмка на подтверждённых входах каждого из трёх объектов, сравнение с фактическим хронометражем и расширение неподдерживаемых политик участка. Несколько физических рёбер с одним `resource_id` пока отклоняются, если не задана подтверждённая общая ориентация. Описание смены обычным текстом не является расписанием для ядра. Значения не выводятся из визуальной ширины схемы и не подставляются по умолчанию.

## Последствия

`v3` позволяет оценить пропускную способность **в пределах введённой модели**. Владелец площадки должен отдельно подтвердить соответствие маршрута, вместимости, календарей и FIFO своему объекту; даже успешный программный тест не подтверждает физическую безопасность. Если регламент иной, новая политика требует отдельной версии событийного контракта и проверки исторических прогонов.
